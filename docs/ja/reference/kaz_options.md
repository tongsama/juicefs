# kaz のオプション

このページは、kaz 版（`tongsama/juicefs`）が `juicefs mount` と、クライアントのオプションを共有する他のコマンドに足した・変えたオプションの一覧です。本家の `_common_options.mdx` には書かず、本家の文書と同じに保っています。こうしておくと、本家の新しい版を取り込むときに文書が衝突しません。

kaz が足したオプションには `kaz-` の接頭辞が付き、help の説明は `[kaz]` で始まります。全部の一覧は `juicefs mount --help` で確かめてください。このページでは、help の説明だけでは足りないものを説明します。

本家の文書には日本語版がありません。このページだけが日本語版で、英語版は `docs/en/reference/kaz_options.md`、中国語版は `docs/zh_cn/reference/kaz_options.md` です。

|項目|説明|
|-|-|
|`--kaz-get-header-timeout=0`|[kaz] ブロックをダウンロードするとき、応答ヘッダを待つ時間の上限です。この時間を過ぎるとその要求をあきらめ、通常の再試行でダウンロードし直します（既定: 0、無効）。`--get-timeout` とは違います。`--get-timeout` はダウンロード全体（応答を待つ時間とデータを受け取る時間）を区切りますが、このオプションはデータが流れ始めるまでの待ちだけを区切ります。そのため、遅くても流れているダウンロードは切りません。この方法で切ったブロックは、その後 5 分間はこの上限なしで取り直します。いつも応答が遅い object でも、再試行のたびに失敗せずに読めるようにするためです。object storage が応答の前にときどき止まる場合（例: Google Drive の上の rclone serve s3）に役立ちます。通常のダウンロードにかかる時間より十分長く設定してください。|
|`--max-deletes=10`|object を削除するバックグラウンドの worker の数です（既定: 10）。正の値では、`max-deletes × 10240` 個の slice を入れられる上限付きのキューを使い、キューが満杯のときは空くまで待ちます。`0` では slice の object を削除しません。負の値では、呼び出し元の中で同期的に削除します。並列数が無制限に**なるわけではありません**。compaction やファイルの書き込みを遅らせることがあるので、起動時に警告を出します。|
|`--kaz-finish-canceled-get`|[kaz] 読み込みが不要になったために（例: 捨てられた先読み）ブロック全体のダウンロードが取り消されたとき、捨てずにダウンロードを最後まで続け、ディスクキャッシュに入れます（既定: false）。まだ始まっていないダウンロードは、これまでどおり取りやめます。この方法で続けるダウンロードは、最大で `--max-downloads` の半分までです。ディスクキャッシュが必要です。|
|`--kaz-writer-flush-timeout=0s`|[kaz] ファイル全体の flush の期限です。既定の `0s` では、未 commit の書き込みを、経過時間の期限なしで待ちます。compaction や削除キューの待ちも含みます。実際の書き込みエラーは、これまでどおり返します。`auto` を指定すると、従来の再試行の回数から決まる期限（最短 5 分）になります。正の時間を指定するとその期限になり、EIO を返すことがあります。負の値や不正な値は受け付けません。このブランチでは、Linux の FUSE サーバーの watchdog も無効にしています。待っている操作に、15 分で別の EINTR を差し込まないようにするためです。kernel からの中断の通知はこれまでどおり伝わりますが、サーバーが中断として強制的に返す応答はなくなります。これはすべての FUSE の要求に当てはまり、バックエンドが止まり続けている間は要求が待ち続けることがあります。writeback の耐久性の考え方と、object への要求の再試行の上限は変わりません。旧名の `--writer-flush-timeout` も、非推奨の別名として使えます。|
|`--kaz-writer-flush-scope=file`|[kaz] `read` と `fallocate` を実行する前に、どの未 commit の書き込みを commit するかを決めます。既定の `file` では、そのファイルの未 commit の書き込みをすべて待ちます（従来の動き）。`range` では、要求が触れる chunk の未 commit の書き込みと、それが依存する前の slice だけを待ち、ファイルの他の部分への書き込みは止めません。VM のイメージのような、大きくてランダムに書かれるファイルでの停滞が短くなります。ファイルのどこかで commit が失敗したことがすでに記録されているか、待っている間に失敗した場合は、これまでどおりそのエラーを返します。範囲の外で後から起きた失敗は、後の read、fsync、close で返ります。そのため `range` では、範囲の外での追記による quota や容量のエラーが、ファイルを伸ばした fallocate 自身ではなく、その後で表に出ることがあります。待つのはファイルハンドルをロックする前なので、同じハンドルを通す読み書きが止まるのは、待っている間に来た書き込みのときだけです。mount（VFS）を通す読み込みと fallocate に当てはまります。SDK や gateway の `pkg/fs` を通す読み込みは、これまでどおりファイル全体を待ちます。`fsync`、`close`、`truncate`、`copy_file_range` は、いつもファイル全体を待ちます。旧名の `--writer-flush-scope` も、非推奨の別名として使えます。|
|`--kaz-meta-write-batch=0`|[kaz] 1 つの chunk の、続けて並んだ未 commit の slice を、1 回の metadata のトランザクションでいくつまで commit するかの上限です。既定の `0` では、1 回のトランザクションで 1 つの slice を commit します（従来の動き）。まとめての commit は、fsync や close を含むすべての commit に当てはまり、chunk の中での作成の順序を保ちます。まとめた commit が何も書く前に失敗した場合（ファイルがない、権限がない、容量不足、quota の超過）は、各 slice が正確なエラーを受け取れるよう、1 つずつ再試行します。結果が分からない失敗（I/O やネットワークのエラー）は再試行せず、slice が 1 つのときと同じく、そのファイルを失敗の状態にします。Redis、SQL、TKV のエンジンに実装しています。TKV のエンジンは change log が有効なとき、SQL のエンジンはまとめると chunk が同期 compaction の閾値を超えるとき、slice を 1 つずつ commit します。旧名の `--meta-write-batch` も、非推奨の別名として使えます。|
|`--kaz-compaction-gc-mode=legacy`|[kaz] `legacy` では、不要になった slice の削除キューの待ちを、これまでどおり残します。`deferred` を指定すると、参照の減少を永続化した後に、上限付きの通知を使って、ローカルの staging を回収してから、待たない形で物理削除をキューに入れます。リモートのキューが満杯でも、永続化した印を残すので、後で受け付けたローカルの回収を止めません。ローカルのエラーや、同じクライアントで staging の PUT が動いている間は、削除の意図を再試行できる状態で残します。`max-deletes` が正の値であること、metadata が書き込めること、バックグラウンドの回復が有効であることが必要です。通知があふれた場合は、すでにある永続化した印と、その定期的な回復に任せます。metadata の形式を足したり、走査の頻度を上げたりはしません。`deferred` を試す前に、書き込みをするすべてのクライアントに、copy・clone の snapshot の保護が入っている必要があります。旧名の `--compaction-gc-mode` も、非推奨の別名として使えます。|
|`--kaz-compaction-scheduler=legacy`|[kaz] `priority` を指定すると、Read や Write ですでに分かっている slice の数を使い、3 つの固定の区分、11 個の worker、inode ごとに 1 つの実行中の仕事、最大 1024 個の実行中・待ちの通知で compaction を受け付けます。書き込みごとの metadata の参照や、全ファイル・全 chunk の走査はしません。通知は助言にすぎず、あふれると、あまり使われていない chunk の作業が後回しになることがあります。2,500 slice での同期 compaction と、手動の compaction の経路は残ります。旧名の `--compaction-scheduler` も、非推奨の別名として使えます。|
|`--kaz-writer-reuse-window=4`|[kaz] 一致しない未 commit の slice を凍結するまでの、候補の古さの幅です。1〜64 の整数で、既定の 4 は従来の動きです。大きくすると、再利用できる途中の slice を長く残せますが、探す手間とメモリが増えます。隙間、書き終えたブロックの書き直し、重なりの順序、明示的な flush の区切りは変わりません。旧名の `--writer-reuse-window` も、非推奨の別名として使えます。|
|`--kaz-writeback-fsync=true`|[kaz] `--writeback` を有効にしているとき、書き込みを完了と返す前に、staging した各ブロックを `fdatasync` し、そのディレクトリを `fsync` します。OS のクラッシュや停電の後も、staging したデータが残るようにするためです。`false` にすると書き込みは速くなりますが、OS のクラッシュで staging したブロックを失う（中身が空のファイルが残る）おそれがあります。旧名の `--writeback-fsync` も、非推奨の別名として使えます。|
|`--kaz-staging-pack`|[kaz] writeback の upload が列に並んでいるとき、同じ chunk の、列で待っている小さな staging の slice（1 block 未満のもの）を 1 つのオブジェクトとして upload し、それらの slice の記録をそのオブジェクトへ向けます。小さなオブジェクトと PUT の回数を減らします。既定は false です。`--kaz-compaction-mode delta` が必要で（それ以外では警告を出して無効にします）、metadata のエンジンは Redis か SQL に限ります。trash が有効（`--trash-days` が 0 でない）の間は行いません。このために upload を遅らせることはなく、すでに待っている slice だけをまとめます。動作中は、変更していないクライアントから reflink のコピー（`copy_file_range`、`cp --reflink`）を行わないでください。|
|`--kaz-skip-unuploaded-delete`|[kaz] slice を削除するとき、このプロセスが upload を一度も始めていない staging の block には、オブジェクトが存在しないので DELETE を送りません。既定は false です。再起動の前に staging された block、upload を一度でも試みた block（試みでオブジェクトができた可能性があります）、直接の upload は、これまでどおり DELETE を送ります。|
