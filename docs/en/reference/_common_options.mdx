#### Data cache related options {#mount-data-cache-options}

|Items|Description|
|-|-|
|`--buffer-size=300`|total read/write buffering in MiB (default: 300), see [Read/Write buffer](../guide/cache.md#buffer-size)|
|`--prefetch=1`|prefetch N blocks in parallel (default: 1), see [Client read data cache](../guide/cache.md#client-read-cache)|
|`--kaz-finish-canceled-get`|[kaz] When a full-block download is canceled because its read is no longer needed (for example, dropped readahead), keep the download running and store the block in the disk cache instead of discarding it (default: false). Downloads that have not started yet are still skipped, and at most half of `--max-downloads` are kept running this way. Requires the disk cache.|
|`--writeback`|upload objects in background (default: false), see [Client write data cache](../guide/cache.md#client-write-cache)|
|`--writer-flush-timeout=0s`|Local investigation branch: whole-file flush deadline. Default `0s` waits for pending commits without an elapsed-time deadline, including compaction and deletion-queue waits. Actual write errors still propagate. `auto` opts into the legacy retry-derived deadline (minimum 5 minutes); a positive duration opts into that deadline and may return EIO. Negative or invalid durations are rejected. The Linux FUSE server watchdog is also disabled in this branch so it cannot inject a separate 15-minute EINTR into pending operations. Kernel interrupt notifications still propagate, but server-forced interruption replies are removed. This applies to all FUSE requests, which can remain pending during a persistent backend stall. This does not change the existing writeback durability model or object-request retry limits.|
|`--writer-flush-scope=file`|Local investigation branch: which pending writes `read` and `fallocate` commit before they run. Default `file` waits for every pending write of the file (prior behavior). `range` waits only for the pending writes of the chunks the request touches, plus earlier slices they depend on, and does not stop writes to other parts of the file; this shortens stalls on large, randomly written files such as VM images. A commit failure anywhere in the file that is already recorded, or occurs while waiting, is still returned; a later failure outside the range is returned by a later read, fsync or close. With `range`, a quota or space error of an out-of-range append can therefore surface after a fallocate that extends the file instead of from it, The wait happens before the file handle is locked, so reads and writes through the same handle are only held for writes that arrive during it. Applies to reads and fallocate through the mount (VFS); SDK and gateway reads through `pkg/fs` still wait for the whole file. `fsync`, `close`, `truncate` and `copy_file_range` always wait for the whole file.|
|`--meta-write-batch=0`|Local investigation branch: maximum number of consecutive pending slices of one chunk committed in a single metadata transaction. Default `0` commits one slice per transaction (prior behavior). Batching applies to every commit, including fsync and close, and keeps the creation order within a chunk. If a batch fails before writing anything (no such file, permission, no space or quota exceeded), its slices are retried one by one so each gets its exact error; a failure whose outcome is unknown (I/O or network error) is not retried and marks the file failed, as for a single slice. Implemented for Redis, SQL and TKV engines; TKV engines commit slices one by one when the change log is enabled, and SQL engines do so when a batch would take a chunk past the synchronous compaction threshold.|
|`--compaction-gc-mode=legacy`|Local investigation branch: `legacy` retains obsolete-slice deletion-queue waiting. Opt-in `deferred` uses bounded hints after durable reference decrement to retire local staging before a nonblocking physical-delete enqueue. Remote queue saturation retains the durable marker and does not block later accepted local retirement. Local errors or active same-client staging PUTs keep deletion intent retryable. Requires positive max-deletes, writable metadata, and enabled background recovery. Hint overflow retains existing durable markers and their existing periodic recovery; it does not add a metadata format or higher-frequency scans. All writable clients must include the copy/clone snapshot guards before evaluating deferred mode.|
|`--compaction-scheduler=legacy`|Local investigation branch: opt-in `priority` uses slice counts already available from Read/Write, 3 fixed buckets, 11 workers, one active job per inode and up to 1024 active/pending hints. No per-write metadata lookup or all-file/chunk scan. Hints are advisory; overflow can postpone cold work. Existing 2500-slice synchronous and manual compaction paths remain.|
|`--writer-reuse-window=4`|Local investigation branch: candidate age distance before an unmatched pending slice is frozen, integer 1..64. Default 4 retains prior behavior. Larger values can retain reusable partial slices longer, with more search/memory work. Gaps, completed-block rewrites, overlap ordering and explicit flush barriers are unchanged.|
|`--writeback-threshold-size=0` <VersionAdd>1.4</VersionAdd>|When `--writeback` is enabled, only blocks smaller than this size will be staged locally; larger blocks are uploaded directly. Default is 0, meaning all blocks are staged.|
|`--writeback-fsync=true`|When `--writeback` is enabled, `fdatasync` each staged block and `fsync` its directory before acknowledging the write, so staged data survives an OS crash or power loss. Set to `false` for higher write performance at the risk of losing staged blocks (left as empty files) on an OS crash.|
|`--upload-delay=0`|When `--writeback` is enabled, you can use this option to add a delay to object storage upload, default to 0, meaning that upload will begin immediately after write. Different units are supported, including `s` (second), `m` (minute), `h` (hour). If files are deleted during this delay, upload will be skipped entirely, when using JuiceFS for temporary storage, use this option to reduce resource usage. Refer to [Client write data cache](../guide/cache.md#client-write-cache).|
|`--upload-hours` <VersionAdd>1.2</VersionAdd>|When `--writeback` is enabled, data blocks are only uploaded during the specified time of day. The format of the parameter is `<start hour>,<end hour>` (including "start hour", but not including "end hour", "start hour" must be less than or greater than "end hour"), where `<hour>` can range from 0 to 23. For example, `0,6` means that data blocks are only uploaded between 0:00 and 5:59 every day, and `23,3` means that data blocks are only uploaded between 23:00 every day and 2:59 the next day.|
|`--cache-dir=value`|directory paths of local cache, use `:` (Linux, macOS) or `;` (Windows) to separate multiple paths (default: `$HOME/.juicefs/cache` or `/var/jfsCache`), see [Client read data cache](../guide/cache.md#client-read-cache)|
|`--cache-mode value` <VersionAdd>1.1</VersionAdd> |file permissions for cached blocks (default: "0600")|
